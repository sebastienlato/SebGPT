## DEC-0001 — Learning-first implementation strategy

- **Date:** 2026-09-06
- **Status:** Accepted
- **Decision:** Build a small GPT-style language model progressively from first principles in Python and PyTorch. PyTorch may supply tensors, autograd, optimization, and low-level neural-network primitives, but the educational architecture will be implemented explicitly before higher-level frameworks are considered.
- **Why:** The project's purpose is to understand modern language models, not to maximize model capability or implementation speed.
- **Alternatives considered:** Wrap a pretrained model or API; use a high-level training/model framework; begin with a complete Transformer and explain it afterward.
- **Consequences:** Progress will be deliberately phased. Some standard components will be reimplemented for clarity. Core architecture changes require explicit discussion and a new decision entry.

- **Date:** 2026-09-06
- **Status:** Accepted
- **Decision:** Use the existing native ARM64 Python.org CPython 3.14.4 installation to create a `.venv` virtual environment in the project root. Do not add a Python version manager while the installed interpreter remains suitable.

## DEC-0007 — First corpus source, manifest, and leakage boundary

- **Date:** 2026-09-06
- **Status:** Accepted
- **Decision:** Build the first corpus from the UTF-8 plain-text artifact for Project Gutenberg eBook #100, *The Complete Works of William Shakespeare*. Target approximately 170,000 words using a fixed eight-play manifest. Train on *Hamlet*, *Romeo and Juliet*, *Macbeth*, *A Midsummer Night's Dream*, *Much Ado About Nothing*, and *Henry V*; validate on *The Tempest*; and reserve *Twelfth Night* for test. Split only at whole-work boundaries. Derive the initial vocabulary from training data only, audit validation/test for unseen characters before tokenization, and report those characters without modifying or adding them.
- **Why:** A single Gutenberg source provides consistent editorial conventions and clearer provenance than the canonical third-party Tiny Shakespeare copy. Multiple plays provide about one million characters of controlled genre variety, while whole-work evaluation tests transfer to unseen text and avoids overlapping-passage leakage. Training-only vocabulary construction prevents validation/test information from influencing learned preprocessing.
- **Alternatives considered:** Use the canonical Tiny Shakespeare file; use one Project Gutenberg novel; use a TinyStories subset; download separate Shakespeare editions; split a concatenated corpus by random or contiguous character ranges; derive the character vocabulary from all splits.
- **Consequences:** Validation and test measurements will be noisier and harder than within-work evaluation. Source acquisition, extraction, counts, hashing, and unseen-character handling require explicit later gates. Validation/test-only characters remain unchanged and may cause an unresolved representation problem until Phase 2 makes a visible decision.

## DEC-0009 — Deterministic eight-play extraction policy

- **Date:** 2026-09-06
- **Status:** Accepted
- **Decision:** Extract each approved play from the pinned raw master by exact full-line body-title and successor-title markers, using recorded absolute positions only as assertions. Include the top-level title; remove the play-local range from the first exact `Contents` line through immediately before the first exact `Dramatis Personæ` line; retain `Dramatis Personæ` and all subsequent dramatic structure and text. Exclude only the consecutive empty CRLF separator lines before the successor marker, then convert retained CRLF pairs to LF with no other normalization. Emit eight separate split-assigned documents and deterministic provenance metadata. Apply the same algorithm to every split and restrict *Twelfth Night* diagnostics under the sealed-test contract. This decision approves the extraction contract as policy but does not authorize implementation.
- **Why:** Exact structural anchors are more robust and auditable than hard-coded line slicing, while assertions against the pinned source detect drift. Removing duplicated local contents avoids training on an artificial index; retaining character and dramatic structure preserves meaningful context. Separate documents enforce whole-work split boundaries without making tokenization decisions.
- **Alternatives considered:** Select by absolute line numbers; omit the work title; retain local contents; remove `Dramatis Personæ`; collapse or strip whitespace; concatenate training plays; special-case validation or test extraction.
- **Consequences:** Extraction must fail on hash, marker-cardinality, ordering, whitespace-boundary, overlap, or verification mismatches. Processed files remain ignored and reproducible from the tracked raw source, approved contract, implementation revision, and recorded hashes. Character inventories remain a later Phase 1 diagnostic; token units, token vocabulary, unseen-input handling, context windows, and all tokenizer behavior remain Phase 2 decisions.

## DEC-0012 — Transactional processed-dataset publication

- **Date:** 2026-09-07
- **Status:** Accepted
- **Decision:** Publish only an already accepted `tuple[ExtractedWork, ...]` and use the authoritative tracked manifest solely to verify dataset identity, exact work/order/split/path assignments, the accepted zero-candidate audit, and populated expected-result ledger values. Encode each `processed_text` directly as strict UTF-8 without transformation. For a first publication, validate every input and expected byte in memory. Open the repository `data` directory without following symlinks and verify its descriptor identity; create each staging directory exclusively relative to a retained, verified parent descriptor, then create every staged file with descriptor-relative `O_CREAT | O_EXCL | O_NOFOLLOW`, verify its regular-file type, and write/read back the exact bytes through that new descriptor. Revalidate every retained directory binding before path-based defense-in-depth verification. Build the complete future `data/processed` tree under the fixed `data/.processed-staging` path, then atomically promote that staging root to `data/processed` with macOS `renameatx_np` using `RENAME_EXCL` and `RENAME_NOFOLLOW_ANY`, relative to an open, identity-verified `data` directory descriptor. The exclusive kernel operation fails if a target wins the race and never replaces it. Capture the `data` and staging device/inode identities when staging is created and use descriptor-relative, no-follow checks to recognize substitution. Darwin provides no inode-conditional or descriptor-only unlink/rmdir operation; therefore a handled transaction failure performs no automatic staging deletion. It preserves the entire failed or suspicious staging state for explicit human resolution rather than risking deletion of an entry or root replaced after an identity check. An exact existing tree is an idempotent no-op; any mismatch, missing or unexpected entry, partial tree, symlink, or pre-existing staging tree fails without overwrite, repair, merge, or deletion of unexplained state. The generated `processing-manifest.json` is deterministic, contains no timestamp or machine-local paths, and remains an ignored derivative subordinate to the tracked manifest. This decision authorizes implementation and temporary-directory tests only; production publication remains separately gated.
- **Why:** Publication should demonstrate how accepted in-memory documents become durable artifacts without duplicating extraction logic, changing bytes, weakening sealed-test controls, or leaving a partially valid dataset after an ordinary failure. Refusing unexplained existing state keeps the small educational pipeline inspectable and makes idempotence explicit.
- **Alternatives considered:** Write files directly into the final tree; overwrite or repair mismatches; atomically replace individual files; regenerate extraction inside the publisher; treat processed files or the generated manifest as authoritative; include timestamps or discovered host details in generated output.
- **Consequences:** The publisher depends only on accepted extracted works plus manifest-declared publication facts and complete expected ledger values. Production publication cannot run until those ledger prerequisites and a committed publisher revision are recorded. Processed outputs remain ignored and reproducible. Any failed publication can leave staging residue that requires explicit human resolution; this is intentional because cleanup completeness is subordinate to identity-safe deletion. Any later automatic cleanup, force/repair mode, or alternate artifact format requires a new decision.

### Accepted amendment (2026-09-07) — Cooperative-workspace threat model

- **Discovery:** Supported Darwin APIs do not provide an atomic operation that both creates a directory and returns a descriptor bound to that exact new directory. `mkdirat` followed by `openat` has a namespace-substitution window. Darwin `renameatx_np` with `RENAME_EXCL` atomically protects the destination but identifies the source by name and cannot condition promotion on a previously verified source inode. The specified directory-tree architecture therefore cannot guarantee safety against an unrelated same-user process deliberately mutating repository namespace entries at those exact windows.
- **Amended threat model:** The accepted guarantee covers Model A, an ordinary/static SebGPT workspace, and Model B, multiple cooperating SebGPT publisher invocations that all obey the repository-local exclusive publication lock. Model C, adversarial namespace mutation by an unrelated process with the same filesystem authority that ignores the protocol, is explicitly outside the publisher guarantee.
- **Lock protocol:** Acquire the empty `data/.publish-lock` presence file atomically and relative to the verified `data` directory with `O_CREAT | O_EXCL | O_NOFOLLOW | O_CLOEXEC`, then hold its descriptor for the complete publication transaction. A cooperating publisher refuses an existing lock without creating staging or target state. Release the verified lock after ordinary success or a clean pre-publication refusal. Preserve the lock together with staging after a crash, construction attempt, uncertain failure, or unverifiable state; later invocations refuse it until explicit human resolution. The lock contains no PID, timestamp, host, user, prose, or other invocation metadata.
- **Guarantee within Models A/B:** Validate inputs and bytes before writing; create staged regular files exclusively without following symlinks; retain descriptor-relative construction as defense-in-depth; make exact reruns idempotent; refuse mismatching, partial, stale, symlinked, or unexpected state; preserve failed staging and uncertainty; atomically refuse an existing final destination; and verify the complete published tree afterward.
- **Boundary:** The publication lock coordinates cooperating SebGPT publishers only. It is not a security boundary and does not prove that an unrelated same-user process cannot mutate `data`. Existing descriptor, identity, no-follow, and no-clobber checks remain useful hardening but must not be described as proof of Model-C security. This amendment supersedes only DEC-0012's threat-model scope; its byte identity, artifact authority, idempotence, failure-preservation, generated-manifest, and production-authorization decisions remain unchanged.

## DEC-0013 — First tokenizer conceptual direction

- **Date:** 2026-09-08
- **Status:** Accepted for Phase 2 design; implementation and production vocabulary construction are not authorized
- **Decision:** SebGPT's first tokenizer uses one Python `str` iteration element, identified by its Unicode code-point integer, per token. It performs no Unicode normalization. It derives and freezes its vocabulary exclusively from the six accepted training works, orders code points by ascending integer value, and assigns contiguous zero-based IDs in that order. Validation cannot add entries, and the sealed test work does not participate. The tokenizer has no unknown, beginning, end, padding, document-separator, reserved, or unused token IDs. An unrecognized code point raises a deterministic content-safe error without replacement, removal, normalization, or vocabulary extension. Supported text, including the empty string and exact whitespace, must satisfy `decode(encode(text)) == text`. Every work remains an independent token stream. Phase 2 leaves the sealed test untokenized and uninspected. Context windows are outside the tokenizer implementation; Phase 4 should introduce next-token window semantics and Phase 8 production sampling and batching unless a later decision changes that boundary. Byte-level and BPE tokenizers are possible later educational comparisons only.
- **Why:** A code-point tokenizer makes token units, vocabulary construction, integer assignment, encoding, decoding, failure behavior, and round trips directly inspectable. The training inventory is small, while the accepted zero-unseen-code-point observation shows corpus compatibility without making test data a vocabulary source or eliminating the need for a generic unknown-input policy. Strict errors and no special tokens preserve exact reversibility and avoid introducing later modeling choices prematurely.
- **Alternatives considered:** Byte-level tokenization; word tokenization; BPE, WordPiece, or Unigram subwords; an unknown token; special document or batching tokens; frequency or first-occurrence ID order; Unicode normalization; deriving vocabulary from all splits.
- **Consequences:** The eventual vocabulary size equals the number of distinct training code points and contains no additional entries. Production vocabulary construction, real ID assignment, implementation, encoding, and statistics remain separately gated. The sealed-test prohibition is stricter during Phase 2 than merely hiding prose: no tokenizer operation or statistic may be applied to it.

## DEC-0015 — First embedding and positional-representation direction

- **Date:** 2026-09-08
- **Status:** Conceptual architecture accepted; detailed contract proposed for independent review
- **Accepted decision:** Use an embedding dimension of 32. Represent the accepted 81-token vocabulary with one explicit learnable token table of shape `(81, 32)` and 2,592 parameters. Use learned absolute positional embeddings with capacity 256, rows `0` through `255`, shape `(256, 32)`, and 8,192 parameters. Add token and position vectors directly, for 10,784 total representation parameters. Implement the future mechanism as one small `torch.nn.Module` containing exactly two manually managed `torch.nn.Parameter` matrices rather than `torch.nn.Embedding`. Initialize the token table first and position table second from the same local CPU `torch.Generator` seeded with 1337, using explicit normal initialization with mean zero and standard deviation `1 / sqrt(32)`. The semantic baseline is CPU `torch.float32` parameters and `torch.long` IDs. Bind construction to tokenizer ID `shakespeare-code-point-v1`, artifact schema 1, vocabulary size 81, canonical artifact path `artifacts/tokenizers/shakespeare-code-point-v1/vocabulary.json`, and artifact SHA-256 `9f4235f9dab3e0361221a90c5ae7ca7fee540760fcc1708964368e6f17d6d70e`; size alone is insufficient. Tiny synthetic single-sequence and batched lookup, gradient, and one-hot-equivalence demonstrations are permitted during later authorized implementation. Maximum positional capacity 256 does not select training context length.
- **Proposed detailed mechanics:** Adopt `docs/EMBEDDING_SPEC.md` as the detailed Phase 3 contract only after independent review, any required correction, and explicit acceptance. Its proposed mechanics define one combined module and `forward` API, a tokenizer-owned immutable vocabulary binding, exact tensor validation and empty-shape behavior, internal position generation, output semantics, local-generator initialization order, CPU bitwise-repeatability scope, two content-safe exception types, thirty-six contract checks, later-phase exclusions, and eighteen separate gates. These details are not accepted merely because they are documented.
- **Why:** A manually indexed parameter table exposes the mathematical mechanism, registration, initialization, shapes, shared rows, and gradient accumulation directly. Width 32 is a small but useful educational representation size. Learned absolute positions reuse the same lookup concept and remain easy to inspect. An exact artifact identity prevents an 81-row table from silently acquiring different token meanings. Local deterministic initialization separates model identity from unrelated global random-number use.
- **Alternatives considered:** Embedding dimensions 8, 16, 64, or 128; `torch.nn.Embedding`; one-hot production inputs; separate token and position modules; sinusoidal positions; RoPE before attention; an unspecified or training-derived positional capacity; implicit initialization; global RNG state; MPS or mixed precision as the baseline; accepting vocabulary size without exact mapping identity; loading Phase 1 corpus data during runtime model construction.
- **Consequences:** Phase 3 contract design is authorized and its accepted constants may not be silently changed. Implementation, parameter construction, tests, context windows, production batching, next-token targets, model/loss/attention work, training, and generation remain unauthorized. The detailed API, authority loader, validation, error, determinism, and test mechanics require independent review before a contract commit or implementation authorization.

## DEC-0016 — Simple non-attention next-token baseline

- **Date:** 2026-09-09
- **Status:** Conceptual architecture accepted; detailed contract proposed for independent review
- **Accepted decision:** Phase 4 uses a minimal linear/log-bilinear language-model baseline over the accepted Phase 3 token-plus-position representation. Each position independently maps its own 32-dimensional representation to 81 logits, with no communication between positions and therefore an effective token context of one token. Examples use equal-length inputs and targets shifted by one token, maximum input length 64, stride 64, and a final variable-length tail whenever at least one adjacent transition remains. Examples are generated deterministically on demand, never persisted, and processed one at a time without padding, batching, or random sampling. The output head is untied and explicit, with weight shape `(32, 81)` and bias shape `(81,)`. Cross-entropy is implemented transparently from logits with stable normalization. The inspected update and bounded run use manual SGD without optimizer infrastructure. Only the six accepted training works update parameters; *The Tempest* is evaluation-only; *Twelfth Night* is completely inaccessible in Phase 4. The primary conceptual baseline is `ln(81)`, and initial/final aggregate training and validation losses are reported without treating training improvement as proof of generalization.
- **Inherited authority:** Preserve tokenizer ID `shakespeare-code-point-v1`, vocabulary size 81, the accepted vocabulary artifact and SHA-256, no special tokens, embedding width 32, token table `(81, 32)`, learned absolute-position table `(256, 32)`, token-plus-position addition, CPU float32 parameters, `torch.long` IDs, exact vocabulary binding, and the accepted embedding implementation. Positional capacity 256 does not change the accepted Phase 4 context length of 64.
- **Why:** This is the smallest model that exposes next-token inputs and targets, logits, probabilities, stable cross-entropy, gradient flow, and explicit parameter updates while preserving a clear experimental control for Phase 5: attention will add cross-position information flow that this baseline intentionally lacks. Stride 64 and a variable tail cover each within-document adjacent transition once without padding or stride-1 duplication.
- **Alternatives considered:** A fixed-window MLP, recurrent or convolutional model, positionwise nonlinear hidden layer, stride-1 or intermediate overlap, dropping the tail, padding or a padding token, materialized examples, rank-two runtime batches, tied output weights, a high-level loss wrapper, `torch.optim`, shuffled traversal, test evaluation, and using validation improvement as a mandatory Phase 4 success condition.
- **Consequences:** The accepted architecture is intentionally limited and must not be described as consuming a 64-token effective context. Both accepted Phase 3 embedding tables and the untied output head are intended to remain trainable, subject to detailed-contract review.
